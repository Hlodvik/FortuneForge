# Game security audit process

Implementation state and remaining acceptance gates, 2026-10-31. Production behavior still requires live verification.

## Initial API pilot scope

The isolated API candidate instruments the shared slot engine and currently hosted games. It keeps existing free-play Craps routes and omits the concurrent paid Craps and Mines host/policy changes; those games need their own release before their specific replay checks can run live. The separate recent-games and presence endpoints are excluded. A stricter new/reset password policy is included with the account risk changes; existing password authentication is unaffected. Clean evidence deletion is disabled for this pilot. IP and city observations are recorded, but they cannot raise pair-review priority until a verified trusted-proxy configuration is enabled. No detector can impose a player restriction automatically.

## Current pass and next gates

1. The single shared slot engine now records paid spin admission, frozen rules, a state event, private settlement and an independent saved-outcome recheck for all 20 titles. The demo ingress also writes a private round and event, then independently replays the saved outcome and bonus progression. Demo spins have no account settlement.
2. All 20 non-slot catalogue paths have local server evidence at their existing coverage level in the [coverage matrix](GAME_SECURITY_OVERHAUL_MATRIX.md). Several terminal-only paths still need separate timed deal/draw events, and some titles need independent command replay. Six in-memory practice paths cannot commit gameplay state and Firestore journal atomically. All four hidden arcade routes are hosted; Snake and the other three arcade engines have database replay checks, with later competition prizes/refunds still separate.
3. The database worker reads completed round evidence, checks its SHA fingerprint and participant money arithmetic, scans the linked engine journal and request receipts for identity, indexed metadata and server-time consistency, and compares event IDs with the transactionally written instance manifest. In this pilot, named database checks cover paid and demo slots; Snake; Asteroids, Flappy and Horse Flight; Blackjack and Three Card Poker; seven paid card games; Keno and Sic Bo; Hearts; competitive Solitaire; Liar's Dice v2; and four practice outcomes. Mines replay and its wallet reconciliation remain outside this release. 2048, Drop Merge, Roulette and Craps replay saved action sequences, with explicit warnings where command arguments or atomic state storage are unavailable. Hearts also checks each intermediate match state and adjacent action. Keno, Sic Bo, paid Hearts, competitive Solitaire and the paid-card families reconcile separate wallet entries, including bounded checks for unexpected round-linked entries where their identifiers allow it. Solitaire's later claim command requeues its match for a fresh pass over the credited wallet entry. A recheck replaces prior second-pass findings, so an old pending warning does not survive a successful later check. Hold'em revenue and wallet entries are checked, including escrow reservations with open-lifecycle coverage. Missing evidence, a deleted intermediate event, or a missing manifest opens a system investigation. Historical rounds without a manifest are labeled legacy coverage. A clean supported replay clears its capture-time pending warning, while non-atomic storage, later prize settlement and other real coverage limits remain visible. The worker records an auditor version and per-round coverage; administrative recheck is available while private evidence remains. Full independent action replay across the catalogue remains a future gate.
4. An integrity case pins originals before cleanup, then copies the complete available summary, private outcome, journal, request intents/results, game-specific operation events and known financial/source references in bounded pages. Unflagged actions and participants remain in the copy. Missing material is visible as capture coverage; a missing request result is marked partial after ten minutes instead of blocking later cases forever. Snake's terminal evidence contains its replay inputs directly; the mutable `snakeGames` source document is not copied as the authoritative outcome. Other game source records have separate retention rules and must be reviewed before any end-to-end deletion claim. The original round, event and request collections are not a substitute for tamper-evident storage outside the same Firestore trust boundary.
5. Every human pair is projected from each clean completed Hold'em hand, paid Hearts match and competitive Solitaire match. At 20 shared instances by default, the worker queues deeper game-specific review and pins a bounded sample. After verified trusted ingress is explicitly enabled, overlapping IP or approximate city can queue review earlier and raise priority. Hold'em has descriptive heads-up decision features; Hearts and Solitaire currently have co-play and network context only. No title yet has a calibrated collusion verdict. Different addresses or VPN use never turn off pair screening.
6. Build and calibrate the remaining detectors on known clean and adversarial data, measure false positives, compare decisions with comparable non-partner play and version thresholds. Only an attributable, evidence-backed risk incident can contribute to player restrictions. Storage or engine discrepancies create unattributed system cases because they can be bugs or infrastructure failures.

## Evidence contract and checks

The server supplies the authoritative clock and instance ID. Authenticated game commands write request intent before the route runs; transaction-backed paths write accepted state and settlement with an engine event. Private evidence includes cards and deck order, reel stops and effective paytable, dice/draw outcomes and hidden boards where the game supplies them. Financial evidence includes wager reservation, balance entries and gross payout with stable IDs where available. Any missing contract field is a coverage gap to resolve per game. Current checks and proposed later screens are:

| Check | When it can flag | Interpretation |
| --- | --- | --- |
| Missing or changed round, engine, or request evidence | Current: next database pass after completion | Unattributed system integrity case; never an automatic player strike |
| Deal/outcome inconsistency | Current: game-specific live checks and named database replay for slots, arcade, table/card, numeric and four practice outcomes; coverage varies by title | Engine bug, altered source or invalid transition; full action replay is still incomplete |
| Wager, pot, payout or wallet mismatch | Current: settlement checks and second-pass Hold'em/slot, Mines, Keno, Sic Bo, paid Hearts and seven paid-card ledger checks; Solitaire claim settlement is checked after its separate claim | Financial discrepancy; Hold'em escrow cash-out conservation remains incomplete until lifecycle close, and some game-specific payout paths remain separate |
| Rejected-command bursts or automation timing | Proposed: rolling windows after enough clean baseline data | Behavioral lead; detector and thresholds are not implemented |
| Coordinated play or transfers | Current: Hold'em, paid Hearts and competitive Solitaire pair queues; proposed calibrated game-specific comparison | Queue for human analysis, not a cheating accusation |
| Shared IP or approximate city | Recorded with request source; used for pair priority only after verified trusted ingress opt-in | Raises scrutiny only; household, venue, carrier NAT and VPN explanations remain plausible |

The investigation worker waits 60 seconds when idle and 10 seconds after it processes work. A completed-round finding should normally appear on the next pass plus Firestore processing time, subject to queue depth, retry backoff and outages. Pending/next-attempt fields keep failed items visible; production latency needs monitoring and a deployment test. Cloud Run's default request-based CPU and scale-to-zero can pause this background worker between requests. Use the guarded API release's `-ContinuousAudit` option for one minimum instance with CPU available outside requests when continuous review is approved; otherwise expect delayed, traffic-dependent processing. A slot admission without settlement is reviewed after two minutes. An authenticated request with no engine event, round evidence or admission is reviewed after two minutes: a missing HTTP result, server failure or apparently accepted command opens an unattributed operational case, while an ordinary 4xx rejection does not. Pair review needs a multi-instance sample (20 shared hands or matches by default) unless network context raises scrutiny earlier; the current queue does not make a cheating finding. Any committed settlement must be reconciled, never silently rewritten by the auditor.

For the initial production pilot, keep `SecurityAuditInvestigations:EnableVerifiedNetworkPairPriority` at its default `false`. IP and `ipSource` remain in private request receipts, and every human pair still accumulates shared-instance counts. After checking the actual ingress peer CIDRs and forwarded header chain, opt in with `SecurityAuditInvestigations__EnableVerifiedNetworkPairPriority=true`, `GameSecurityRequests__IpMode=TrustedProxyChain`, `GameSecurityRequests__RequireTrustedProxy=true`, and the verified `GameSecurityRequests__TrustedProxyNetworks__0` (plus subsequent numbered CIDRs). Startup rejects the pair-priority opt-in without strict trusted-proxy configuration. Only receipts marked `trusted-proxy-chain` can contribute an IP or city priority signal. An incorrect trusted-peer list can make game commands return 503, so verify it against the live ingress before enabling.

## What the data can establish

Stored authoritative cards, wagers, actions, rules and wallet entries can establish internal consistency and reproduce supported outcomes. A complete action stream shows what the server recorded and when it received commands. Some current games have only a terminal state or a non-atomic practice journal, which cannot reproduce every decision. The data cannot establish intent, who was physically at a device, off-platform communication or a precise location from IP. A stored PRNG seed reproduces a shuffle but does not prove unbiased randomness or secrecy before play. Historical rounds from before instrumentation cannot be reconstructed.

Each investigation records evidence **for**, evidence **against**, alternative explanations, sample size, missing coverage and reviewer decision. Reviewers can clear or confirm an attributable incident with reasons and an audit trail. Network data remains private to authorized reviewers.

## Retention and release gates

Clean round detail becomes eligible for deletion seven days after its evidence review, once the database pass and any pair review release their holds. The raw engine journal, linked request records and settled slot admissions are then purged through a second hold-checked process. Unlinked authenticated requests are reviewed after two minutes and their original intents/results become eligible for deletion after at least seven days, subject to the configured clean retention period and link/hold checks. A linked request whose separate HTTP result is still absent keeps its completed round queued through the two-minute grace period. An operational case first copies an unlinked request and any result; its open copy remains held even after the original seven-day deadline. Open/incomplete cases stay held; cleared cases keep copied detail 30 days after resolution; confirmed attributable incidents retain it indefinitely. Summaries and financial ledgers remain. Game-specific source documents, such as settled game state, follow separate retention rules and are not removed by this round/raw cleanup. Deployment must publish the Firestore indexes and rules, configure trusted ingress proxies before relying on client IP, verify recovery and backfill boundaries, and measure actual retention, journal size and detection latency before production claims. Optional city context requires an operator-provided dataset; the default resolver does not call an external geolocation service.
