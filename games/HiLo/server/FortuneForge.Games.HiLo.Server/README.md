# Hi-Lo server package

The engine, secure random draw and every debit/credit run on the server. The client sends a wager or direction only. Each draw independently chooses rank 1–13 and suit 0–3 with `RandomNumberGenerator.GetInt32`; cards are replaced. Only revealed cards exist in state. The package never generates or persists an unrevealed deck, random seed or future sequence.

## Host integration

The packaged worker registers `AddHiLoServer`, the signed `AddGameWalletClient("hi-lo")`, and `MapHiLo`. The shared API authenticates the account and forwards the original public routes with a signed worker assertion. Its local registration can still serve practice; paid requests must stay on the configured Hi-Lo worker. Register `FirestoreDb` in the worker. Worker configuration requires `GameWallet:Url` and `GameWallet:SigningKey`; the account service needs the matching `GameWallet:Games:hi-lo:SigningKey`, `AllowAccountBalanceRead=true`, and `AllowWagerReservations=true`, using standard wallet ledgers (`LegacySlotLedger=false`).

`Features:HiLoEnabled` is false by default. When disabled, the worker rejects new wagers/guesses/skips after checking recorded operations; existing-round reads, cashouts and exact accepted replays remain available. Forwarding must therefore remain active during a pause. Disabled GET with no prior round returns503. Existing-round GET exposes `enabled:false`. Configure read/write rate-limit policy names through `HiLoServerOptions`.

`ForcePractice` or the existing `X-FortuneForge-Practice: true` convention selects the separate practice store. Practice never accesses Firestore, production credentials, account wallets or payment data. Paid requests use signed generic account reads and settlements. The account service owns canonical `userBalances/{userId}_slotsCredits` and all balance transaction writes; the Hi-Lo package never writes those collections.

All mutating requests require `X-FortuneForge-Game: hi-lo`, JSON content and an approved exact Origin (same origin is accepted). Configure only the actual host origins in `AllowedOrigins`; use credentialed CORS solely for those origins. Attach existing host authentication and rate limits. In hosted HTTPS the account cookie remains the host's secure cookie; the local practice sample intentionally binds only HTTP loopback and never authenticates a paid account.

## HTTP contract

* `GET /api/games/hi-lo/session` returns `{practice,walletBalanceCents,limits,round}`. No active/latest round yields `round:null`.
* `POST /api/games/hi-lo/rounds` accepts `{operationId,wagerCents}`.
* `POST /api/games/hi-lo/rounds/{roundId}/actions` accepts `{operationId,expectedRevision,choice}` with `higher`, `lower`, `skip`, or `cashout`.

Both writes return a session snapshot. Cents are integers. Rank strings are `ace`, `two` … `king`; suits are `clubs`, `diamonds`, `hearts`, `spades`. Status is `active`, `lost`, `cashedOut` or `maximumReturn`. `higher.multiplier`/`lower.multiplier` are the **total cumulative multiplier after a successful choice**, with limits applied; `projectedReturnCents` is the exact payable return after cent flooring. `probability` includes equal ranks as losing outcomes. `currentReturnCents` includes the stake at the beginning, so immediate cashout refunds the wager.

Each write must generate one operationId (16–128 ASCII letters, digits, hyphens or underscores) and preserve the *exact command* until confirmed. Retries with that ID and same payload return the exact original response, even after subsequent actions. Reusing an ID for another payload returns409 `operation_conflict`. After recovery of an older command, GET session obtains the current state. Preserve pending operations across browser refresh; never silently invent a new operationId after timeout.

Concurrent different actions at the same expectedRevision permit one transition; the other returns409 `stale_revision` or `operation_pending` while the original command is awaiting confirmation. Concurrent starts permit one active wager. A round cannot incur a second debit or payout. Cashout and automatic limit settlement credit exactly once. Error bodies contain `{code,message}`. `insufficient_funds`, `round_active`, `stale_revision`, `operation_pending`, `round_finished` and `invalid_choice` are409; inaccessible round404; malformed request400; unauthenticated401; disallowed origin403; transient/uncertain service failure503 `retry_required`. Responses set no-store.

## Persistence and operation journal

The adapter first saves an immutable command/outcome intent in `hiLoOperations` and locks the player's `hiLoPlayers` head. A new round reserves its wager through the signed wallet before revealing its initial card. Terminal actions complete that reservation, including a loss with zero payout. Legacy active rounds already paid their wager and use a credit-only direct settlement. Intermediate actions use zero-value wallet operations. The adapter finalizes revealed state, exact response, receipt, event, security evidence and completed history only after the wallet confirms the frozen request.

If either process loses a reply, an exact retry or session read repeats the original wallet operation and finishes the saved intent. A competing command cannot bypass the pending intent. Insufficient funds detected before drawing also creates a durable rejection without drawing or calling the wallet; its original key remains rejected after a top-up. A declined intent never reveals a card. Revealed engine history is replayed on state reads through `HiLoEngine.ValidateRevealedHistory`; finalized receipts and response projections are checked on replay. Original request observations survive recovery reads through the shared `FirestoreGameAudit` writer. Legacy schema-one operation/event/ledger records retain their original validation and responses. A surviving ledger or event without its operation fails closed before RNG or wallet calls. Existing terminal history is checked before requesting a legacy-round credit. Collections `hiLoPlayers`, `hiLoOperations`, `hiLoEvents` must be server-only. Production access rules and deployment are separate from local package implementation.

Practice state uses an exclusive cross-process lock file, a flushed temporary file and atomic replacement to commit the wallet, current revealed round, ledger and operation response together. It survives service restart. Configure a dedicated writable persistent path for the host; avoid network shares without atomic rename/locking guarantees. The practice file retains its complete operation journal and grows over time; it is intended for local/development play, not a production database. Paid operation/event documents are deliberately retained for replay and audit. A future retention/archival job must retain operation identity and exact response for at least the host's published replay window, and preserve ledger audits; no unreviewed TTL is installed here.

The sample has no production credentials and creates a 256-bit random HttpOnly SameSite Strict practice cookie, with separate wallet state for each cookie. The cookie persists30days and the file has no cash value. Start it from this repository with `dotnet run --project games/HiLo/samples/FortuneForge.Games.HiLo.Web` (port5203). The package sample's `.data` path and logs are ignored.

Run `dotnet test games/HiLo/tests/FortuneForge.Games.HiLo.Server.Tests` to execute practice, HTTP and actual Firestore transaction tests. The test fixture starts an isolated localhost Firestore emulator from an already installed Firebase emulator JAR and Java, on an unused port; it never connects to live Firestore. Alternatively supply localhost `FIRESTORE_EMULATOR_HOST`. Missing local emulator prerequisites fail visibly rather than skip paid-wallet tests.
